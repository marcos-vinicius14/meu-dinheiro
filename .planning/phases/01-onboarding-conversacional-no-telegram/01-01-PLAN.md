# Plan 01-01: Máquina de Estados Finitos, SessionStore em Memória e Roteador de Mensagens/Callbacks

## Objetivo

Implementar a base arquitetural da Máquina de Estados Finitos (FSM) no daemon do Telegram Bot (`apps/bot`), incluindo o `SessionStore` em memória com sincronização concorrente via `sync.RWMutex`, rotina de expurgo ativo por TTL (30 minutos) e roteamento de atualizações para mensagens e `CallbackQuery` (botões inline), com cancelamento imediato via `/cancelar`.

## Contexto

- `.planning/phases/01-onboarding-conversacional-no-telegram/01-CONTEXT.md` (Decisões D-01, D-02, D-03)
- `apps/bot/internal/bot/bot.go` (Entrada de updates e mensagens do Telegram)
- `apps/bot/internal/client/api_client.go` (Cliente HTTP da API interna)

1. Criar o subpacote `apps/bot/internal/bot/fsm/` e o arquivo `types.go`:
   - Declarar o tipo `State string` e as constantes de estado:
     - `StateIdle State = "IDLE"`
     - `StateWaitingBalance State = "WAITING_BALANCE"`
     - `StateWaitingCycleDay State = "WAITING_CYCLE_DAY"`
     - `StateWaitingFixedExpenses State = "WAITING_FIXED_EXPENSES"`
     - `StateWaitingEmergencyFundChoice State = "WAITING_EMERGENCY_FUND_CHOICE"`
     - `StateWaitingSavingsTarget State = "WAITING_SAVINGS_TARGET"`
     - `StateWaitingInvestmentChoice State = "WAITING_INVESTMENT_CHOICE"`
     - `StateWaitingInvestmentInput State = "WAITING_INVESTMENT_INPUT"`
   - Declarar as structs de dados da sessão:
     - `FixedExpenseData`: `Description string`, `Amount float64`, `CategoryName string`
     - `InvestmentData`: `Ticker string`, `Quantity float64`, `AveragePrice float64`
     - `Session`:
       - `TelegramID int64`
       - `ChatID int64`
       - `FirstName string`
       - `Username string`
       - `CurrentState State`
       - `InitialBalance float64`
       - `CycleStartDay int`
       - `FixedExpenses []FixedExpenseData`
       - `EmergencyFundMonths int` (6 ou 12)
       - `MonthlyEssentialCost float64`
       - `TargetSavings float64`
       - `Investments []InvestmentData`
       - `LastActiveAt time.Time`

2. Criar `apps/bot/internal/bot/fsm/store.go`:
   - Declarar `type SessionStore struct`:
     - `mu sync.RWMutex`
     - `sessions map[int64]*Session`
     - `ttl time.Duration`
   - Construtor `NewSessionStore(ttl time.Duration) *SessionStore`:
     - Inicializa o mapa; se `ttl <= 0`, default é `30 * time.Minute`.
   - Métodos thread-safe:
     - `Get(telegramID int64) (*Session, bool)`
     - `GetOrCreate(telegramID int64, chatID int64, firstName, username string) *Session`
     - `Set(session *Session)`
     - `Delete(telegramID int64)`
     - `Touch(telegramID int64)`: atualiza `LastActiveAt = time.Now().UTC()`
     - `EvictExpired() int`: remove sessões onde `time.Since(s.LastActiveAt) > ttl` e retorna a quantidade expurgada
     - `StartEvictionWorker(ctx context.Context, interval time.Duration)`: executa loop em goroutine com `time.NewTicker(interval)` chamando `EvictExpired()` até `ctx.Done()`

3. Criar testes unitários em `apps/bot/internal/bot/fsm/store_test.go`:
   - Testar ciclo básico: `GetOrCreate`, `Set`, `Get`, `Delete`.
   - Testar concorrência pesada (20+ goroutines simulando múltiplos usuários com leituras e escritas simultâneas sob `go test -race`).
   - Testar expiração via `EvictExpired` manipulando `LastActiveAt` e verificando remoção de sessões antigas e retenção de sessões ativas.
</action>

<action>
1. Criar `apps/bot/internal/bot/fsm/fsm.go`:
   - Definir interface `TelegramSender` para desacoplar envio de mensagens nos testes:
     ```go
     type TelegramSender interface {
         Send(c tgbotapi.Chattable) (tgbotapi.Message, error)
         Request(c tgbotapi.Chattable) (*tgbotapi.APIResponse, error)
     }
     ```
   - Definir `type FSM struct`:
     - `store *SessionStore`
     - `sender TelegramSender`
     - `client *client.APIClient`
     - `logger *slog.Logger`
   - Construtor `NewFSM(store *SessionStore, sender TelegramSender, client *client.APIClient, logger *slog.Logger) *FSM`
   - Implementar método principal `HandleUpdate(ctx context.Context, update *tgbotapi.Update) (handled bool, err error)`:
     - Tratar `update.CallbackQuery`:
       - Responder imediatamente com `tgbotapi.NewCallback(update.CallbackQuery.ID, "")` via `sender.Request`.
       - Obter sessão pelo `update.CallbackQuery.From.ID`.
       - Roteador para o callback conforme `session.CurrentState`.
     - Tratar `update.Message`:
       - Extrair texto limpo.
       - Se comando for `/cancelar`:
         - Chamar `store.Delete(user.ID)`.
         - Responder no chat: `"❌ Onboarding cancelado. Você pode reiniciar a qualquer momento enviando /start."`.
         - Retornar `handled = true`.
       - Se for `/start` (sem token de auth) ou o usuário tiver sessão com estado != `StateIdle`: delegar para a FSM.
       - Se o usuário não tiver sessão e o comando não for `/start`: retornar `handled = false` para permitir outros comandos globais (`/ajuda`, `/status`).

2. Atualizar `apps/bot/internal/bot/bot.go`:
   - Adicionar campos `sessionStore *fsm.SessionStore` e `fsm *fsm.FSM` na struct `Bot`.
   - No `NewBot`:
     - Instanciar `sessionStore := fsm.NewSessionStore(30 * time.Minute)`.
     - Instanciar `fsm := fsm.NewFSM(sessionStore, api, client, logger)`.
   - Em `Start`:
     - Iniciar `go b.sessionStore.StartEvictionWorker(ctx, 5*time.Minute)` antes de entrar no loop de polling ou webhook.
   - Em `handleUpdate`:
     - Suportar tanto `update.Message != nil` quanto `update.CallbackQuery != nil`.
     - Tentar `b.fsm.HandleUpdate(ctx, update)`:
       - Se `handled == true`, encerra processamento do update.
       - Se `handled == false`, passa para o `handleMessage` existente (mantendo `/start auth_<token>`, `/ajuda`, `/status`).

3. Criar testes unitários em `apps/bot/internal/bot/fsm/fsm_test.go`:
   - Mock/fake de `TelegramSender` para capturar mensagens e callbacks.
   - Testar envio de `/cancelar` no meio de uma sessão ativa: verifica que sessão é deletada e mensagem de cancelamento é enviada.
   - Testar recepção de `CallbackQuery`: verifica envio de resposta vazia de callback (`NewCallback`) e despacho para o estado ativo.
   - Testar que `/start auth_xyz` retorna `handled = false` ou é ignorado pela FSM para manter o login web intacto.
</action>

## Must Haves

<must_haves>
### Truths
- D-01: O SessionStore armazena, recupera e remove dados de sessão em memória com segurança concorrente garantida por `sync.RWMutex`.
- D-02: Estratégia de evicção de cache por TTL ativo implementada via `time.Ticker` em background a cada 5 minutos expurgando sessões inativas há mais de 30 minutos.
- D-03: Suporte ao comando `/cancelar` a qualquer momento durante o onboarding para resetar e expurgar a sessão em memória imediatamente.
- Updates do Telegram contendo `CallbackQuery` são confirmados e roteados para a FSM.
- O fluxo de autorização web `/start auth_<token>` continua funcionando normalmente.

### Artifacts
- `apps/bot/internal/bot/fsm/types.go` fornecendo definições de estados e estruturas de sessão.
- `apps/bot/internal/bot/fsm/store.go` fornecendo `SessionStore` com controle de concorrência e evicção por TTL.
- `apps/bot/internal/bot/fsm/store_test.go` cobrindo concorrência (`-race`) e expurgo de sessões.
- `apps/bot/internal/bot/fsm/fsm.go` fornecendo o despachante de eventos e roteador de mensagens e callbacks.
- `apps/bot/internal/bot/fsm/fsm_test.go` cobrindo `/cancelar`, `CallbackQuery` e bypass de comandos externos.

### Prohibitions
- Não usar variáveis globais não sincronizadas para gerenciar o estado da conversa.
- Não persistir estados intermediários e rascunhos no banco de dados PostgreSQL.
- Não quebrar o fluxo de autenticação 1-clique do navegador (`/start auth_<token>`).
- Não reter locks (`mu.Lock`) durante chamadas de rede ou I/O.
</must_haves>
