# Plan 02-01: Endpoints Internos de Simulação What-If, Check-in Diário Idempotente e Métodos no APIClient

## Objetivo

Expor na API Go (`apps/api`) os endpoints internos protegidos por chave secreta (`X-Internal-Secret`) para Simulação What-If de 12 ciclos (`POST /internal/transactions/simulations`), Check-in Diário com gravação idempotente (`POST /internal/transactions/checkin`) e Atualização de Saldo de Conta Bancária (`POST /internal/bank-accounts/balance`). Validar toda a suíte com testes de integração reais contra PostgreSQL 18 via Testcontainers, e implementar os tipos e métodos correspondentes no `client.APIClient` do bot (`apps/bot`) com testes unitários cobrindo serialização e tratamento de erros.

## Contexto

- `.planning/phases/02-comandos-do-motor-preditivo-opera-o-di-ria/02-CONTEXT.md` (Decisões D-05 a D-12)
- `apps/api/internal/transaction/service.go` (Métodos de domínio `SimulatePurchase` e `DailyCheckIn`)
- `apps/api/internal/bankaccount/repository.go` (Método `Update` de saldo de contas)
- `apps/api/internal/botapi/handler.go` (Roteamento de endpoints internos)
- `apps/api/tests/integration/test_support.go` (Infraestrutura de Testcontainers Postgres 18)
- `apps/bot/internal/client/api_client.go` (Cliente HTTP consumido pelo bot)

     - **Cenário 3: Ajuste de Saldo de Conta Bancária (`POST /internal/bank-accounts/balance`)**:

       - Validar resposta `200 OK` com saldo da conta atualizado.
       - Consultar `GET /internal/users/context-by-telegram` e validar que `total_liquid_balance` reflete o novo saldo de R$ 4.800,00.
     - **Cenário 4: Segurança e Validações de Borda**:
       - Validar que chamadas sem `X-Internal-Secret` retornam `403 Forbidden`.
       - Validar que `telegram_id` inexistente retorna `404 Not Found` em todos os endpoints.
       - Validar que simulação com `amount <= 0` retorna `400 Bad Request`.
       - Validar que check-in com valores de despesas negativas retorna `400 Bad Request`.

## Must Haves

<must_haves>
### Truths
- `POST /internal/transactions/simulations` calcula o que acontece com o S2S e liquidez em até 12 ciclos futuros, identificando o ciclo mais crítico (menor S2S) e alertando sobre risco de déficit (D-05, D-06, D-08).
- `POST /internal/transactions/checkin` consolida as despesas do dia, calcula a economia diária e projeta o S2S de amanhã com persistência idempotente (`UPSERT`) em `tb_check_in_snapshots` (D-09, D-11, D-12).
- `POST /internal/bank-accounts/balance` atualiza o saldo bancário líquido da conta do usuário para sanidade de liquidez (D-10).
- Todos os endpoints exigem cabeçalho `X-Internal-Secret` e retornam 403 se ausente ou incorreto.
- Todos os testes de integração backend rodam contra container real do PostgreSQL 18 via Testcontainers sem mocks de banco.

### Artifacts this phase produces
- `apps/api/internal/botapi/simulation.go`: Endpoints e handlers de simulação what-if.
- `apps/api/internal/botapi/checkin.go`: Endpoints e handlers de check-in diário.
- `apps/api/internal/botapi/balance.go`: Endpoint de ajuste de saldo bancário.
- `apps/api/tests/integration/internal_bot_api_predictive_test.go`: Bateria de testes de integração com Testcontainers.
- `apps/bot/internal/client/api_client.go`: Métodos `SimulatePurchase`, `DailyCheckIn` e `AdjustAccountBalance`.
- `apps/bot/internal/client/api_client_test.go`: Testes unitários do cliente HTTP.

### Prohibitions
- Não utilizar mocks de banco de dados (`sqlmock`) em nenhuma etapa.
- Não usar `float64` nas operações financeiras dentro da API (`apps/api`), preservando `money.Money` com Banker's rounding HalfEven.
- Não permitir duplicação de snapshots de check-in para o mesmo dia e usuário.
</must_haves>
